## 4. Metric age at capture — NOT fixed-age data

Every snapshot here is a **lifetime cumulative** reading taken at import time, not a views@7d or views@30d measurement. The age distribution below is why that distinction matters: these videos were between days and years old when first observed.

| | |
|---|---|
| videos with a first snapshot | 234 |
| age at first capture — min | 2 days |
| age at first capture — median | 237 days |
| age at first capture — max | 1358 days |
| captured before day 7 | 2 |
| captured before day 30 | 6 |

**Only 2 video(s) were first observed before day 7 and 6 before day 30.** A true `views@7d` series can therefore only be built going forward, from videos posted after collection began. Treating these readings as fixed-age would measure elapsed exposure, not performance (plan section 5.4).

### Client-secret rotation — effect on existing tokens

Prepared, **not performed** (owner approval required).

| Credential | Effect of rotating the client secret |
|---|---|
| **TikTok access token** (24 h) | Keeps working until it expires. |
| **TikTok refresh token** (365 d) | **This is the risk.** The refresh call authenticates with `client_key` + `client_secret`. Once the secret is rotated, the stored secret in `.env` is stale, and the next refresh fails. |
| **Recovery** | Update `TIKTOK_CLIENT_SECRET` in `.env` **before** the current access token expires. The refresh token itself is unaffected — it is not re-issued by rotation. |
| **If the window is missed** | The access token expires, the refresh fails against the stale secret, and the account needs one interactive re-authorisation. No data is lost; the 234 rows and their snapshots are already stored. |

**Safe sequence:** rotate in the TikTok portal → immediately update `.env` →
force a refresh and confirm it succeeds. Doing it right after a successful
refresh leaves nearly 24 hours of margin.

The Meta app secret is not yet used by any stored token, so rotating it now
costs nothing.

## 8. What this does and does not establish

**Established.** 234 videos and 234 snapshots imported with zero validity
problems, matching the API exactly; a working daily schedule whose due-check
survives process restarts; and a corpus whose fixed-age limitations are
explicit in both the data and the code that reads it.

**Not established.** The seven-day unattended run. The schedule has been
tested, not endured — the Phase 2 acceptance criterion requires seven actual
consecutive days, and no amount of testing substitutes for elapsed time.
That clock starts from the first scheduled pass, not from this report.

## 9. Blocker found: the live data is on the wrong machine

The backfill ran against the **Windows workstation's** PostgreSQL, because
that is where `VIRALLAB_DB_URL` pointed during the interactive setup.

| | videos | snapshots | credentials |
|---|---|---|---|
| Windows workstation (intermittent) | 234 | 234 | 1 |
| Ubuntu server (always on) | 0 | 0 | **0** |

The daily schedule is running inside the API process **on the Ubuntu
server**, where there is no credential — so it correctly idles and records
nothing. Meanwhile the data sits on a machine that is switched off much of
the time.

**The seven-day unattended criterion cannot be met in this configuration.**
Collection has to run where the always-on machine is.

Two residues were also removed while checking this, both from pre-guard test
runs: a synthetic `test_creator` with 2 videos in the Windows application
database, and 2 seed videos plus a batch from the Phase 1 round-trip on the
server. Neither was real data; both would have polluted creator baselines.
The test-database guard added earlier prevents a recurrence.

### Resolving it requires an owner decision

Moving collection to the server means putting the TikTok **client secret and
refresh token on the Ubuntu machine**. That is a deliberate security choice,
not a detail, so it is not being done unilaterally. The options:

1. **Move collection to the server** — copy `TIKTOK_CLIENT_KEY`/`SECRET` into
   the server's `.env` (already 0600) and re-run the backfill there. It is
   idempotent on `(platform, external_id)`, so it re-collects cleanly rather
   than duplicating. The Windows copy then becomes a development dataset.
2. **Keep collection on Windows** — only viable if that machine is genuinely
   on every day, which contradicts the hardware assumption the whole
   architecture is built on.

Option 1 is the only one consistent with the design. It needs approval.

## Migration method

One transaction, all-or-nothing: a partial migration would leave plausible
looking but wrong counts. Original primary keys and `captured_at` timestamps
were inserted **verbatim**.

> **This copied observations; it did not re-collect them.** A fresh backfill
> would have stamped every snapshot with the migration time and destroyed the
> observation history — the very thing fixed-age anchors depend on
> (plan §5.4). The migrated snapshots still carry their original 12:08:14
> capture time.

The payload travelled by SFTP as a `0600` file and was deleted from both ends
afterwards, so the credential never appeared on a command line, in a process
list or in shell history. A guard aborts the migration if any non-test
creator already exists on the target, so real data could not be overwritten.

## Live collection on the server

A real pass was then run on Ubuntu: **234 seen, 0 new, 234 snapshots**. Zero
new videos is the correct result — the collector recognised every existing
row and appended a second observation rather than duplicating. The database
now holds **702 snapshots across three distinct capture times**, which is the
beginning of a genuine trajectory.

Restart behaviour was verified directly: after restarting the API, `due()`
returns **False** and the scheduler resumes without re-running the completed
pass. The check reads `collection_runs`, so it is durable across restarts
rather than depending on an in-memory timer.

## Split-brain prevention

Collecting from both machines would fork the dataset into two partial
histories — worse than not collecting at all. Three measures:

1. Windows `.env` sets `VIRALLAB_COLLECTION_ENABLED=0`.
2. `collect_tiktok_once()` raises `CollectionDisabled` on any host where that
   flag is off, covering manual invocation as well as the scheduled loop.
   **Verified live: Windows refuses.**
3. A regression test asserts the refusal.

Windows continues as the GPU worker, which never touches the database
directly — it reaches the server over TLS.

## Credential handling

Server `.env` is `-rw------- rastlyn:rastlyn` and carries the app
credentials. The `/status/collection` endpoint exposes run history and
credential **health** (`needs_reauth`, `expires_at`) but never token values.

**Client-secret rotation is prepared but NOT performed** — it needs owner
approval, and the sequencing in §7 applies: rotate, update the server `.env`
within the 24-hour access-token window, then force a refresh to confirm.
